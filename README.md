# ТЗ 6. OTP-сервис

REST API выдачи и проверки одноразовых кодов с защитой от перебора и спама запросами,
**личный кабинет абонента** («кто и когда запрашивал коды на мой номер», заморозка выдачи кодов)
и **модуль оценки рисков**, который в реальном времени распознаёт ботов (SMS pumping, перебор кодов)
и объясняет каждое решение на дашборде. Осенний хакатон INAI 2026. Обязательная часть соответствует
ТЗ и уточнениям v1.1 (CLARIFICATIONS_RU.md, §6).

**Зачем кабинет.** Самые частые способы украсть SMS-код — выманить его звонком «из банка»
или перехватить после подмены SIM. Абонент видит в кабинете каждый запрос кода (с именем
сервиса и IP), неверные вводы и блокировки, а если что-то не так — одним нажатием замораживает
выдачу кодов всем сервисам: пока заморозка действует, выманивать и перехватывать нечего.

**Зачем модуль рисков.** Обязательные лимиты ТЗ одинаковы для всех и считаются по одному номеру.
Бот, который рассылает SMS на тысячи разных номеров (SMS pumping — компания платит за каждое SMS),
через них проходит: каждый номер для сервиса «новый». Модуль рисков смотрит на поведение IP целиком —
сколько номеров, идут ли они подряд, вводятся ли коды, сколько ошибок — и ловит такого бота на
**6-м номере**, показывая, какие признаки сработали и сколько денег он стоил бы.

## Для проверки жюри

**Запуск — одна команда, без зависимостей** (Python 3.10+, состояние в памяти процесса):

```bash
python3 run.py
```

1. **IP клиента берётся из подключения.** Клиенты с 127.0.0.1 и 127.0.0.2 получают раздельные
   IP-лимиты (20 проверок в минуту на каждый адрес). `X-Forwarded-For` по умолчанию
   игнорируется, адреса из примеров в коде не прописаны. Это проверяется тестом с настоящими
   подключениями с обоих адресов (`test_ip_limit_is_per_connection_address`).
2. **`advance` — реальное ожидание.** Сервис работает на системных часах, поэтому достаточно
   подождать указанное число секунд. Тестовый режим с подменой часов — `python3 run_scenarios.py`:
   прогоняет сценарии в формате жюри на сервисе в том же процессе, `advance` сдвигает часы мгновенно
   (подробнее — ниже). Отдельного API для управления временем нет.
3. **OTP берётся из `outbox/sms.jsonl`** в корне репозитория: одна строка JSON на каждую выдачу,
   `{"ts": "...", "msisdn": "...", "code": "..."}`. Путь можно переопределить переменной `OTP_OUTBOX`.

**Docker Compose (сервис + Redis):**

```bash
docker compose up --build                                                    # Windows / macOS
docker compose -f docker-compose.yml -f docker-compose.host.yml up --build   # Linux: для проверки IP
```

В обычном режиме Docker подключения с localhost проходят через docker-proxy, и сервис видит адрес
шлюза Docker вместо 127.0.0.1/127.0.0.2. На Linux надстройка `docker-compose.host.yml` запускает
сервис в сети хоста, и IP из подключения сохраняется. `outbox/sms.jsonl` в обоих режимах
появляется в корне репозитория.

> В Linux и macOS команда — `python3`; в Windows — `python` или `py`.

Сервис слушает `http://localhost:8000`:
кабинет абонента — **http://localhost:8000/cabinet**, дашборд безопасности — **http://localhost:8000/dashboard**,
вкладка рисков — **http://localhost:8000/dashboard#risk**.

- **Доставка «SMS»** (тестовый транспорт в формате жюри): каждая выдача дописывается строкой
  `{"ts": "2026-11-21T09:00:00+06:00", "msisdn": "996770730000", "code": "012345"}`
  в `outbox/sms.jsonl` в корне репозитория (путь — `OTP_OUTBOX`); дублируется в консоль.
  Сервис этот файл не читает, публичного HTTP-метода получения кода нет.
- **Журнал безопасности** — `logs/security.log` (без кодов).

**Тестовый режим с подменой часов.** Сценарии в формате жюри (`scenarios/*.json`: request /
capture_delivery / advance / parallel). Каждый сценарий — на свежем сервисе в том же процессе,
с подменяемыми часами, поэтому `advance 900` выполняется мгновенно; код перехватывается из outbox
сценария, `client_ip` передаётся в слой API напрямую:

```bash
python3 run_scenarios.py                         # все scenarios/scenarios_*.json
python3 run_scenarios.py путь/к/сценариям.json   # любой файл того же формата
```

Атака на сервис (в другом терминале, пока сервис запущен):

```bash
python3 attack.py                                   # локальный запуск
docker compose exec otp python attack.py --pause 0  # в Docker
```

Тесты (244 шт.: сценарии × {память, Redis через fakeredis}, сценарии жюри, HTTP-слой, IP из подключения, дашборд, кабинет, модуль рисков):

```bash
pip install -r requirements.txt
python3 -m pytest -q
```

## Модуль рисков за 3 минуты

Нужны два терминала и браузер. Запуск без Docker — так демо-скрипты могут изображать разных пользователей
с разных IP (см. «Почему `OTP_TRUSTED_PROXIES=127.0.0.1`» ниже).

**1. Сервис** (терминал 1):

```bash
DASHBOARD_TOKEN=demo OTP_TRUSTED_PROXIES=127.0.0.1 python3 run.py
```

В PowerShell: `$env:DASHBOARD_TOKEN="demo"; $env:OTP_TRUSTED_PROXIES="127.0.0.1"; python run.py`.

**2. Дашборд** — открыть **http://localhost:8000/dashboard?token=demo#risk**.
Пока трафика нет, вкладка пустая: «Пока нет данных — запустите attack.py».

**3. Трафик** (терминал 2) — один из вариантов:

```bash
# полный сюжет для защиты (3–4 мин): обычные пользователи + три атаки по очереди
python3 demo_traffic.py --scenario demo --token demo

# только SMS pumping-бот с отдельного IP (~1,5 мин)
python3 attack.py --only pumping --client-ip 45.13.7.200 --token demo

# обязательные атаки ТЗ — без изменений, все с 127.0.0.1
python3 attack.py
```

**4. Что смотреть на вкладке «Риски»:**

- **Плитки** — уровень угрозы, IP под наблюдением, тревоги, «≈ N сом потрачено ботами», конверсия.
- **«Подметание» номеров** (окно 5 мин) — обычные пользователи дают случайное облако точек,
  pumping-бот рисует линию.
- **Граф «IP → номера»** — у бота «звезда» из десятков лучей, у пользователя один луч.
- **Топ IP** → клик по строке → **карточка IP** с разбором балла по причинам и отметками порогов 30 и 60.
- **Лента тревог** — «Средний» на 5-м номере бота, «Высокий» на 6-м.
- Кнопка **«Сводка за 10 минут»** — текст про все инциденты: тип атаки, IP, диапазон номеров,
  стоимость, момент обнаружения.

**Без сервера**, чтобы просто посмотреть логику в консоли:

```bash
python3 -m app.risk.demo            # сюжет на подменённых часах: таблица IP с причинами и тревоги
```

Полный сценарий выступления, цифры для слайда и ответы на вопросы жюри — в **[DEMO.md](DEMO.md)**.

## API

### `POST /otp/send`

```json
{ "msisdn": "996770730000", "service": "INAI Bank" }
```

`service` — необязательное имя сервиса, запросившего код (до 40 символов); абонент видит его в истории.
| Код | Тело | Когда |
|---|---|---|
| 200 | `{"status":"sent","expires_in":120,"next_send_in":30}` | код выдан (сам код в ответе не возвращается) |
| 429 | `{"status":"resend_too_early","retry_after":N}` | не прошла задержка 30/60/120 с |
| 429 | `{"status":"send_limit_exceeded","retry_after":N}` | уже 3 выдачи в окне (t−600, t] |
| 423 | `{"status":"msisdn_blocked","retry_after":N}` | номер заблокирован |
| 423 | `{"status":"msisdn_frozen"}` (+ `retry_after`, если заморозка на срок) | владелец заморозил коды в кабинете |
| 400 | `{"status":"bad_request","error":"..."}` | неверный JSON / формат номера / `service` |

### `POST /otp/verify`

```json
{ "msisdn": "996770730000", "code": "012345" }
```

Порядок проверок: IP-лимит → формат → блокировка номера → код.

| Код | Статус                             | Когда                                                                           |
| --- | ---------------------------------- | ------------------------------------------------------------------------------- |
| 200 | `verified`                         | код верный (атомарно погашен)                                                   |
| 401 | `invalid_code` (+ `attempts_left`) | неверный код, кода нет или он уже использован                                   |
| 410 | `code_expired`                     | прошло ≥120 с с выдачи                                                          |
| 423 | `msisdn_blocked` + `retry_after`   | 5-я ошибка к активному коду (уже этот ответ) и всё время блокировки [t, t+900)  |
| 429 | `ip_rate_limited` + `retry_after`  | 21-й verify с IP за (t−60, t] — любой verify, в том числе с ошибкой формата     |
| 400 | `bad_request`                      | неверный JSON, нет полей, номер не 12 цифр с 996, код не строка ровно из 6 цифр |

На всех 423/429 выставляется заголовок `Retry-After`. Номер — строка ровно из 12 цифр, начинается с `996`;
код — строка ровно из 6 цифр (ведущие нули значимы, `000000` допустим, число `12345` — ошибка формата).

Модуль рисков на эти ответы **не влияет**: они одинаковы с ним и без него (это проверяет отдельный тест).

Пример:

```bash
curl -X POST localhost:8000/otp/send   -H "Content-Type: application/json" -d '{"msisdn":"996770730000"}'
tail -n 1 outbox/sms.jsonl
curl -X POST localhost:8000/otp/verify -H "Content-Type: application/json" -d '{"msisdn":"996770730000","code":"012345"}'
```

## Что сделано (обязательная часть)

| #   | Требование                                                                  | Реализация                                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 6 цифр из `secrets`, TTL 120 с, одноразовый, новый запрос аннулирует старый | `secrets.randbelow(10**6)`; после успеха запись удаляется; новый `send` перезаписывает запись номера                                                                                                                                              |
| 2   | Хранится только HMAC, сравнение за постоянное время                         | `HMAC-SHA256(secret, "msisdn:code")`, `hmac.compare_digest`. Номер в сообщении — хеш одного номера бесполезен для другого                                                                                                                         |
| 3   | Задержка 30/60/120 с, ≤3 send на номер за 10 мин                            | скользящее окно отметок времени отправок                                                                                                                                                                                                          |
| 4   | 5 неверных → блок 15 мин; ≤20 verify/мин с IP                               | счётчик неверных кодов к активному OTP (сбрасывается при успехе; нет кода / истёк / ошибка формата не считаются); на 5-й ошибке сразу 423, текущий код аннулируется, `send` → 423. IP-лимит — скользящее окно по всем номерам, проверяется первым |
| 5   | Параллельные verify одним кодом → успешен ровно один                        | каждая операция — атомарная секция под блокировкой номера (проверить и удалить код за один шаг); сценарий жюри O16 (20 параллельных → 1×200, 19×401) проходит                                                                                     |
| 6   | Журнал событий безопасности без кодов                                       | JSON-строки в `logs/security.log`: `otp_issued`, `send_rate_limited`, `verify_failed`, `verify_expired`, `verify_success`, `msisdn_blocked`, `verify_rejected_blocked`, `verify_ip_rate_limited`. Номер маскируется (`9965*****456`), кодов нет   |
| 7   | `attack.py`: перебор одного номера и распределённый по 50 номерам           | см. ниже                                                                                                                                                                                                                                          |

### attack.py

Обе атаки по 1000 попыток. Чтобы доказать, что защита действительно останавливает атаку,
а не «просто не повезло», скрипт **подмешивает настоящий код** (перехватывает его из `outbox/sms.jsonl`)
в середину перебора. Успех атаки = хотя бы один ответ 200.

Пример вывода:

```
=== Атака 1: перебор кода для одного номера ===
  попыток всего        : 1000
  200 (код подошёл)    : 0
  401 (неверный)       : 4      <- 4 неверных
  423 (номер заблок.)  : 16     <- с 5-й ошибки номер заблокирован, даже настоящий код не принят
  429 (лимит по IP)    : 980    <- после 20 проверок/мин
  РЕЗУЛЬТАТ: атака остановлена

=== Атака 2: распределённый перебор по 50 номерам с одного IP ===
  401 (неверный)       : 20     <- по 1 попытке на номер, блок номера не срабатывает...
  429 (лимит по IP)    : 980    <- ...но срабатывает лимит по IP
  РЕЗУЛЬТАТ: атака остановлена
```

Между атаками пауза 61 с, чтобы окно IP-лимита сбросилось (`--pause 0` — без паузы).
Опции: `--url`, `--attempts`, `--workers`, `--numbers`, `--only single|distributed|pumping`.
Код выхода `0` — все атаки остановлены.

**Режим `--only pumping`** (запускается только явно, в обычный прогон не входит) — третья атака:
бот медленно (≈1,5 с) запрашивает коды на номера подряд и не вводит их. Параметры: `--client-ip`
(отправить `X-Forwarded-For`), `--range-prefix`, `--count`, `--interval`, `--jitter`, `--token`.
В конце печатает честный вердикт: базовая защита рассылку не остановила (лимит send — только на номер),
а модуль рисков обнаружил бота на N-м номере; в боевом режиме остальные SMS были бы отклонены, экономия ≈X сом.

## Личный кабинет абонента — `/cabinet`

Веб-страница (адаптирована под телефон) и API. Вход — по SMS-коду, через тот же механизм OTP.

| Метод                    | Тело / заголовок                                | Ответ                                                                             |
| ------------------------ | ----------------------------------------------- | --------------------------------------------------------------------------------- |
| `POST /cabinet/code`     | `{"msisdn"}`                                    | как `/otp/send`: код для входа в кабинет                                          |
| `POST /cabinet/login`    | `{"msisdn","code"}`                             | 200 `{"status":"verified","token","expires_in":1800}`; ошибки — как `/otp/verify` |
| `GET /cabinet/me`        | `Authorization: Bearer <token>`                 | статус номера (`frozen`, `blocked_until`) и история (последние 50 событий)        |
| `POST /cabinet/freeze`   | `{"duration": 3600 \| 86400 \| 604800 \| null}` | заморозить коды на час / сутки / неделю / до разморозки                           |
| `POST /cabinet/unfreeze` | —                                               | снять заморозку                                                                   |
| `POST /cabinet/logout`   | —                                               | завершить сессию                                                                  |

Как устроено:

- **Заморозка** действует только на коды для внешних сервисов: `/otp/send` отвечает 423
  `msisdn_frozen`, уже выданный код аннулируется. Номера, которые никто не замораживал
  (в том числе тестовые номера жюри), ведут себя строго по ТЗ.
- **Код для входа в кабинет** выдаётся и при заморозке — иначе её нельзя было бы снять. У него
  отдельный код и отдельный счётчик выдач с теми же лимитами: злоумышленник, заваливая номер
  запросами кодов, не может помешать владельцу войти в кабинет. Защита от перебора общая:
  5 неверных вводов блокируют номер целиком, IP-лимит 20/мин действует и на вход в кабинет.
- **Сессия** — случайный токен (`secrets.token_urlsafe`), в хранилище лежит только его SHA-256,
  срок жизни 30 минут.
- **История** — события номера (выдача кода с именем сервиса и IP, неверные вводы, блокировки,
  отказы, заморозка) хранятся в том же хранилище (память или Redis) 30 дней, последние 50.
  Кодов в истории нет.
- В дашборде безопасности события кабинета видны отдельным фильтром «Кабинет абонента».

## Модуль оценки рисков — `app/risk/`

Адаптивная защита: вместо одинаковых правил для всех — оценка риска каждого IP по понятным признакам.
Каждое решение объяснимо: у каждого балла есть название, вес и фраза с цифрами
(«коды запрошены на 37 номеров за 10 мин»).

**Режим наблюдения.** Модуль только наблюдает: он не меняет ответы `/otp/send` и `/otp/verify`,
поэтому сценарии жюри проходят так же, как без него. Уровень «Высокий» — это тревога и подпись
«в боевом режиме было бы отклонено». Включить применение решений — следующий шаг (см. «Что не успели»).

### Признаки (по одному IP, окно 10 минут)

| Признак                    | Условие                                                                   | Баллы     |
| -------------------------- | ------------------------------------------------------------------------- | --------- |
| Веер номеров               | коды запрошены на >5 / >15 разных номеров                                 | +20 / +40 |
| Номера подряд              | ≥5 номеров, у >50% есть «сосед» (последние 4 цифры отличаются на 1–10)    | +25       |
| SMS без подтверждения      | ≥5 SMS, подтверждено <10% (главный признак SMS pumping)                   | +25       |
| Частые ошибки              | ≥5 проверок, ≥50% неудачны                                                | +25       |
| Новый IP для номера        | номер раньше подтверждался с другого IP                                   | +15       |
| Попытки к заблокированному | ≥3 verify к заблокированному номеру                                       | +15       |
| Лимит IP                   | срабатывал лимит 20 verify/мин                                            | +15       |
| Ночь                       | 01:00–06:00 по Бишкеку (слабый признак: сам по себе не поднимает уровень) | +10       |

Балл — сумма, не больше 100. **Низкий** < 30 ≤ **Средний** < 60 ≤ **Высокий**.
«В бою»: низкий — обычный режим, средний — задержки ×2, высокий — отказ 429 и тревога.
Тревога создаётся, когда уровень IP повышается.

Как это работает на демо-сюжете: pumping-бот — «Высокий» на 6-м номере (90 баллов); распределённый
перебор — 100; подбор кода к одному номеру — «Средний» (его и так останавливает базовая защита);
офис или университет, где 8 человек сидят за одним IP, — «Низкий» (+20 за веер, отказа не будет).

### Как подключён

```
OTPService ─► SecurityLog.event() ─► security.log, дашборд «Журнал»
                     │ add_sink: событие + номер (до маскирования) + время из часов сервиса
                     ▼
             асинхронная очередь ─► RiskEngine (в памяти) ─► GET /api/risk/* ─► вкладка «Риски»
```

- Событие кладётся в очередь без ожидания (`put_nowait`); если очередь переполнена, оно отбрасывается
  и учитывается в счётчике `dropped`. Медленный или сломанный модуль не задерживает и не роняет ответы.
- Если модуль не смог запуститься, сервис работает без него; `RISK_ENABLED=0` выключает его явно.
- Полный номер живёт только до обработки события: модуль хранит HMAC-псевдоним, последние 4 цифры
  и маску `+996700***456`. Кодов и их HMAC модуль не получает. Ни один ответ `/api/risk/*` не содержит
  полного номера (это проверяют тесты).

### API модуля рисков

Все маршруты — `GET`, с той же авторизацией, что `/api/security/events` (`DASHBOARD_TOKEN`).
Ответы: 200, 400 (неверный параметр), 401, 404 (`/ip` для неизвестного IP), 503 `risk_disabled` / `risk_error`.

| Маршрут              | Параметры                    | Что отдаёт                                                                          |
| -------------------- | ---------------------------- | ----------------------------------------------------------------------------------- |
| `/api/risk/overview` | `window` (3600)              | уровень угрозы, IP по уровням, тревоги, SMS / подозрительные / стоимость, конверсия |
| `/api/risk/timeline` | `window` (3600), `step` (60) | события по минутам, разбитые по уровням                                             |
| `/api/risk/ips`      | `limit` (20), `min_level`    | топ IP: балл, причины, номера, SMS, спарклайн, действие «в бою»                     |
| `/api/risk/ip`       | `ip`                         | карточка IP: разбор балла, статистика, последние события (номера в маске)           |
| `/api/risk/scatter`  | `window` (1800)              | точки «время × последние 4 цифры номера»                                            |
| `/api/risk/graph`    | `window` (600)               | граф «IP → номера»                                                                  |
| `/api/risk/alerts`   | `limit` (50), `since_id`     | лента тревог                                                                        |
| `/api/risk/summary`  | `window` (600)               | сводка инцидента: текст и список инцидентов                                         |

```bash
curl -s -H 'X-Dashboard-Token: demo' 'localhost:8000/api/risk/ips?min_level=medium'
```

### Сводка инцидента и LLM

`/api/risk/summary` всегда собирает сводку **по шаблону** из агрегатов: тип инцидента (SMS pumping,
подбор кода к номеру, распределённый подбор), IP, балл, диапазон номеров в маске, число SMS и стоимость,
на каком номере и через сколько секунд появилась тревога, что было бы сделано в боевом режиме.

Если задан `RISK_LLM_API_KEY`, тот же список инцидентов (только агрегаты, без номеров, кодов и сырых
событий) отправляется в LLM, чтобы переписать его понятным языком для дежурного. Таймаут 5 с, кеш 30 с,
при любой ошибке — шаблон. LLM ничего не решает: она только пересказывает уже посчитанные факты.

### Почему `OTP_TRUSTED_PROXIES=127.0.0.1` в демо

Локально весь трафик идёт с `127.0.0.1`, и обычные пользователи слились бы с ботом в один IP.
`demo_traffic.py` и `attack.py --client-ip` отправляют `X-Forwarded-For` с выдуманными IP, а сервер
принимает этот заголовок только от доверенного прокси. Без `OTP_TRUSTED_PROXIES` заголовок игнорируется,
как и должно быть в бою. В Docker запросы с хоста приходят не с `127.0.0.1`, поэтому полный демо-сюжет
удобнее запускать без Docker; вкладка «Риски» в Docker работает (модуль включён по умолчанию),
а `docker compose exec otp python attack.py --pause 0` покажет атакующий IP на уровне «Высокий».

## Бонусы

### Хранение в Redis с TTL

`app/store.py` — `RedisStore` с тем же интерфейсом, что и `MemoryStore`, бизнес-логика не менялась.

- Все ключи пишутся с нативным TTL (`SET ... PX`): код — 120 с + окно, счётчики отправок — 10 мин,
  блокировка — 15 мин, окно IP-лимита — 60 с. Redis сам удаляет просроченное.
- Ключи: `otp:otp:<msisdn>` (только HMAC + срок), `otp:sends:<msisdn>`, `otp:fails:<msisdn>`,
  `otp:block:<msisdn>`, `otp:ipverify:<ip>`.
- **Атомарность при нескольких экземплярах сервиса**: секция «прочитать-проверить-записать» идёт под
  распределённой блокировкой (`SET lock NX PX 5000` со случайным токеном; снятие — compare-and-delete
  через `WATCH/MULTI`, чтобы не снять чужую). Блокировки отдельные для номера и для IP и берутся
  по очереди, а не вложенно, поэтому взаимоблокировка невозможна.
- **Fail closed**: если Redis недоступен, `send`/`verify` отвечают `503` — коды не выдаются
  и не проверяются «вслепую», лимиты нельзя обойти, уронив Redis. `/health` тоже отдаёт 503.

### Дашборд событий безопасности — `/dashboard`

Страница без внешних CDN (работает офлайн), светлая/тёмная тема, две вкладки.

**«Журнал»** (открывается по умолчанию), обновляется каждые 2 с:

- плитки: выдано кодов, успешные проверки, неверные вводы, блокировки, срабатывания лимитов;
- график событий по минутам за 30 минут (с подсказками и табличным видом);
- подозрительные IP, последние блокировки номеров (активна / снята);
- лента событий с фильтрами (выдача, неверные вводы, блокировки, лимиты, успешные).

Данные — `GET /api/security/events?limit=N` (JSON). Кодов там нет, номера замаскированы.

**«Риски»** (`/dashboard#risk`): плашка «Режим наблюдения», плитки, сводка инцидента, динамика риска
по уровням, «подметание» номеров (окно 5/30 мин), граф «IP → номера», топ IP с карточкой и разбором
балла, лента тревог; на кнопке вкладки — счётчик новых тревог. Время везде по Бишкеку, все данные
выводятся через `textContent`.

Защита обеих вкладок токеном — переменная `DASHBOARD_TOKEN`.

### Docker Compose

`docker compose up --build` поднимает Redis 7 (без записи на диск, с healthcheck) и сервис
(стартует после готовности Redis, свой healthcheck). Папка `./outbox` смонтирована в контейнер,
поэтому `outbox/sms.jsonl` появляется в корне репозитория на хосте. Ключ HMAC — `OTP_SECRET` в окружении или `.env`.
Переменные `RISK_*` в `docker-compose.yml` не передаются: модуль рисков работает с настройками по умолчанию.

## Решения и допущения

- **Почему без FastAPI.** Стандартная библиотека — запуск без `pip install`, нет риска,
  что у жюри не соберутся зависимости. `ThreadingHTTPServer` обрабатывает запросы параллельно,
  атомарность обеспечивает блокировка в `OTPService`.
- **Счётчик 5 ошибок** накапливается по номеру между выдачами кода (новый `send` его не сбрасывает,
  сбрасывает только успешная проверка или блокировка) — иначе перевыпуск кода давал бы лишние попытки.
- **IP клиента** берётся из сокета. `X-Forwarded-For` принимается только от адресов из
  `OTP_TRUSTED_PROXIES` (по умолчанию — ни от кого), берётся последний адрес цепочки. Произвольный
  заголовок игнорируется, поэтому подменой `X-Forwarded-For` обойти лимит нельзя (есть тест).
- **Без Redis состояние в памяти процесса**: при перезапуске коды и лимиты сбрасываются. С Redis — переживает перезапуск сервиса.
- **История для дашборда** (последние 5000 событий) хранится в памяти процесса; полный журнал — в `logs/security.log`.
- Если не задан `OTP_SECRET`, ключ HMAC генерируется случайно при старте.
- **Модуль рисков только наблюдает**: зачётные сценарии жюри шлют запросы с одного IP на номера подряд —
  ровно то, что модуль считает подозрительным. Применять его решения к таким запросам значило бы сломать
  проверку по ТЗ, поэтому решения показываются как рекомендации.
- **Состояние модуля рисков в памяти**: окно признаков — 10 минут, после перезапуска оценка начинается заново.

## Что не успели / идеи

- История событий для дашборда хранится в памяти каждого экземпляра; при нескольких экземплярах
  её стоит перенести в Redis Stream (туда же — состояние модуля рисков).
- Лимит на `send` по IP и подсети. Сейчас такую рассылку **обнаруживает** модуль рисков (pumping-бот
  пойман на 6-м номере), но не **останавливает**.
- Режим enforce для модуля рисков: «Средний» — задержки ×2, «Высокий» — отказ 429, с белым списком
  доверенных IP для тестовых стендов.
