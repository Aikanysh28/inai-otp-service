# ТЗ 6. OTP-сервис

REST API выдачи и проверки одноразовых кодов с защитой от перебора и спама запросами.
Осенний хакатон INAI 2026. Поведение соответствует ТЗ и уточнениям v1.1 (CLARIFICATIONS_RU.md, §6).

## Запуск (одна команда)

**Вариант 1 — Docker Compose (сервис + Redis):**

```bash
docker compose up --build
```

**Вариант 2 — без Docker:** нужен только Python 3.10+, внешних зависимостей нет,
состояние хранится в памяти процесса.

```bash
python run.py
```

Сервис слушает `http://localhost:8000`, дашборд — **http://localhost:8000/dashboard**.

* **Доставка «SMS»** (тестовый транспорт в формате жюри): каждая выдача дописывается строкой
  `{"ts": "2026-11-21T09:00:00+06:00", "msisdn": "996770730000", "code": "012345"}`
  в `outbox/sms.jsonl` в корне репозитория (путь — `OTP_OUTBOX`); дублируется в консоль.
  Сервис этот файл не читает, публичного HTTP-метода получения кода нет.
* **Журнал безопасности** — `logs/security.log` (без кодов).

Сценарии в формате жюри (`scenarios/*.json`: request / capture_delivery / advance / parallel).
Каждый сценарий — на свежем сервисе с подменяемыми часами, поэтому `advance 900` выполняется мгновенно:

```bash
python run_scenarios.py                         # все scenarios/scenarios_*.json
python run_scenarios.py путь/к/сценариям.json   # любой файл того же формата
```

Атака на сервис (в другом терминале, пока сервис запущен):

```bash
python attack.py                                   # локальный запуск
docker compose exec otp python attack.py --pause 0 # в Docker
```

Тесты (103 шт.: сценарии × {память, Redis через fakeredis}, сценарии жюри, HTTP-слой, дашборд):

```bash
pip install -r requirements.txt
python -m pytest -q
```

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` / `HOST` | `8000` / `0.0.0.0` | адрес сервера |
| `OTP_SECRET` | случайный на каждый запуск | ключ HMAC |
| `OTP_LOG_DIR` | `logs` | папка журнала безопасности |
| `OTP_OUTBOX` | `outbox/sms.jsonl` | файл тестового SMS-транспорта |
| `OTP_TRUSTED_PROXIES` | пусто | IP через запятую, от которых принимается `X-Forwarded-For` (напр. `127.0.0.1` для стенда жюри) |
| `REDIS_URL` | пусто (память) | напр. `redis://localhost:6379/0` — хранить состояние в Redis (`pip install redis`) |
| `DASHBOARD_TOKEN` | пусто (без защиты) | если задан, дашборд открывается как `/dashboard?token=...` |

## API

### `POST /otp/send`
```json
{"msisdn": "996770730000"}
```
| Код | Тело | Когда |
|---|---|---|
| 200 | `{"status":"sent","expires_in":120,"next_send_in":30}` | код выдан (сам код в ответе не возвращается) |
| 429 | `{"status":"resend_too_early","retry_after":N}` | не прошла задержка 30/60/120 с |
| 429 | `{"status":"send_limit_exceeded","retry_after":N}` | уже 3 выдачи в окне (t−600, t] |
| 423 | `{"status":"msisdn_blocked","retry_after":N}` | номер заблокирован |
| 400 | `{"status":"bad_request","error":"..."}` | неверный JSON / формат номера |

### `POST /otp/verify`
```json
{"msisdn": "996770730000", "code": "012345"}
```
Порядок проверок: IP-лимит → формат → блокировка номера → код.

| Код | Статус | Когда |
|---|---|---|
| 200 | `verified` | код верный (атомарно погашен) |
| 401 | `invalid_code` (+ `attempts_left`) | неверный код, кода нет или он уже использован |
| 410 | `code_expired` | прошло ≥120 с с выдачи |
| 423 | `msisdn_blocked` + `retry_after` | 5-я ошибка к активному коду (уже этот ответ) и всё время блокировки [t, t+900) |
| 429 | `ip_rate_limited` + `retry_after` | 21-й verify с IP за (t−60, t] — любой verify, в том числе с ошибкой формата |
| 400 | `bad_request` | неверный JSON, нет полей, номер не 12 цифр с 996, код не строка ровно из 6 цифр |

На всех 423/429 выставляется заголовок `Retry-After`. Номер — строка ровно из 12 цифр, начинается с `996`;
код — строка ровно из 6 цифр (ведущие нули значимы, `000000` допустим, число `12345` — ошибка формата).

Пример:
```bash
curl -X POST localhost:8000/otp/send   -H "Content-Type: application/json" -d '{"msisdn":"996770730000"}'
tail -n 1 outbox/sms.jsonl
curl -X POST localhost:8000/otp/verify -H "Content-Type: application/json" -d '{"msisdn":"996770730000","code":"012345"}'
```

## Что сделано (обязательная часть)

| # | Требование | Реализация |
|---|---|---|
| 1 | 6 цифр из `secrets`, TTL 120 с, одноразовый, новый запрос аннулирует старый | `secrets.randbelow(10**6)`; после успеха запись удаляется; новый `send` перезаписывает запись номера |
| 2 | Хранится только HMAC, сравнение за постоянное время | `HMAC-SHA256(secret, "msisdn:code")`, `hmac.compare_digest`. Номер в сообщении — хеш одного номера бесполезен для другого |
| 3 | Задержка 30/60/120 с, ≤3 send на номер за 10 мин | скользящее окно отметок времени отправок |
| 4 | 5 неверных → блок 15 мин; ≤20 verify/мин с IP | счётчик неверных кодов к активному OTP (сбрасывается при успехе; нет кода / истёк / ошибка формата не считаются); на 5-й ошибке сразу 423, текущий код аннулируется, `send` → 423. IP-лимит — скользящее окно по всем номерам, проверяется первым |
| 5 | Параллельные verify одним кодом → успешен ровно один | каждая операция — атомарная секция под блокировкой номера (проверить и удалить код за один шаг); сценарий жюри O16 (20 параллельных → 1×200, 19×401) проходит |
| 6 | Журнал событий безопасности без кодов | JSON-строки в `logs/security.log`: `otp_issued`, `send_rate_limited`, `verify_failed`, `verify_expired`, `verify_success`, `msisdn_blocked`, `verify_rejected_blocked`, `verify_ip_rate_limited`. Номер маскируется (`9965*****456`), кодов нет |
| 7 | `attack.py`: перебор одного номера и распределённый по 50 номерам | см. ниже |

### attack.py

Обе атаки по 1000 попыток. Чтобы доказать, что защита действительно останавливает атаку,
а не «просто не повезло», скрипт **подмешивает настоящий код** (перехватывает его из `outbox/sms.jsonl`)
в середину перебора. Успех атаки = хотя бы один ответ 200.

Пример вывода:
```
=== Атака 1: перебор кода для одного номера ===
  попыток всего        : 1000
  200 (код подошёл)    : 0
  401 (неверный)       : 4      <- 4 неверных
  423 (номер заблок.)  : 16     <- с 5-й ошибки номер заблокирован, даже настоящий код не принят
  429 (лимит по IP)    : 980    <- после 20 проверок/мин
  РЕЗУЛЬТАТ: атака остановлена

=== Атака 2: распределённый перебор по 50 номерам с одного IP ===
  401 (неверный)       : 20     <- по 1 попытке на номер, блок номера не срабатывает...
  429 (лимит по IP)    : 980    <- ...но срабатывает лимит по IP
  РЕЗУЛЬТАТ: атака остановлена
```
Между атаками пауза 61 с, чтобы окно IP-лимита сбросилось (`--pause 0` — без паузы).
Опции: `--url`, `--attempts`, `--workers`, `--numbers`, `--only single|distributed`.
Код выхода `0` — все атаки остановлены.

## Бонусы

### Хранение в Redis с TTL
`app/store.py` — `RedisStore` с тем же интерфейсом, что и `MemoryStore`, бизнес-логика не менялась.

* Все ключи пишутся с нативным TTL (`SET ... PX`): код — 120 с + окно, счётчики отправок — 10 мин,
  блокировка — 15 мин, окно IP-лимита — 60 с. Redis сам удаляет просроченное.
* Ключи: `otp:otp:<msisdn>` (только HMAC + срок), `otp:sends:<msisdn>`, `otp:fails:<msisdn>`,
  `otp:block:<msisdn>`, `otp:ipverify:<ip>`.
* **Атомарность при нескольких экземплярах сервиса**: секция «прочитать-проверить-записать» идёт под
  распределённой блокировкой (`SET lock NX PX 5000` со случайным токеном; снятие — compare-and-delete
  через `WATCH/MULTI`, чтобы не снять чужую). Блокировки отдельные для номера и для IP и берутся
  по очереди, а не вложенно, поэтому взаимоблокировка невозможна.
* **Fail closed**: если Redis недоступен, `send`/`verify` отвечают `503` — коды не выдаются
  и не проверяются «вслепую», лимиты нельзя обойти, уронив Redis. `/health` тоже отдаёт 503.

### Дашборд событий безопасности — `/dashboard`
Страница без внешних CDN (работает офлайн), обновляется каждые 2 с, светлая/тёмная тема.
* плитки: выдано кодов, успешные проверки, неверные вводы, блокировки, срабатывания лимитов;
* график событий по минутам за 30 минут (с подсказками и табличным видом);
* подозрительные IP, последние блокировки номеров (активна / снята);
* лента событий с фильтрами (выдача, неверные вводы, блокировки, лимиты, успешные).

Данные — `GET /api/security/events?limit=N` (JSON). Кодов там нет, номера замаскированы.
Защита токеном — переменная `DASHBOARD_TOKEN`.

### Docker Compose
`docker compose up --build` поднимает Redis 7 (без записи на диск, с healthcheck) и сервис
(стартует после готовности Redis, свой healthcheck). Папка `./outbox` смонтирована в контейнер,
поэтому `outbox/sms.jsonl` появляется в корне репозитория на хосте. Ключ HMAC — `OTP_SECRET` в окружении или `.env`.

## Решения и допущения

* **Почему без FastAPI.** Стандартная библиотека — запуск без `pip install`, нет риска,
  что у жюри не соберутся зависимости. `ThreadingHTTPServer` обрабатывает запросы параллельно,
  атомарность обеспечивает блокировка в `OTPService`.
* **Счётчик 5 ошибок** накапливается по номеру между выдачами кода (новый `send` его не сбрасывает,
  сбрасывает только успешная проверка или блокировка) — иначе перевыпуск кода давал бы лишние попытки.
* **IP клиента** берётся из сокета. `X-Forwarded-For` принимается только от адресов из
  `OTP_TRUSTED_PROXIES` (по умолчанию — ни от кого), берётся последний адрес цепочки. Произвольный
  заголовок игнорируется, поэтому подменой `X-Forwarded-For` обойти лимит нельзя (есть тест).
* **Без Redis состояние в памяти процесса**: при перезапуске коды и лимиты сбрасываются. С Redis — переживает перезапуск сервиса.
* **История для дашборда** (последние 5000 событий) хранится в памяти процесса; полный журнал — в `logs/security.log`.
* Если не задан `OTP_SECRET`, ключ HMAC генерируется случайно при старте.

## Что не успели / идеи

* История событий для дашборда хранится в памяти каждого экземпляра; при нескольких экземплярах
  её стоит перенести в Redis Stream.
* Лимит на `send` по IP (защита от рассылки SMS на много разных номеров с одного адреса).
