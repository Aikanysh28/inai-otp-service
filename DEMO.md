# Демо для защиты: OTP-сервис + модуль оценки рисков

Сюжет на 3–4 минуты: обычные пользователи, затем бот **SMS pumping**, подбор кода и распределённая атака.
Базовый сервис отвечает строго по ТЗ. Модуль рисков **только наблюдает**: замечает бота, считает
потерянные деньги и говорит, что сделал бы в боевом режиме.

## Запуск (три команды)

```bash
# 1. сервис: токен админки + доверие X-Forwarded-For от 127.0.0.1 (так демо-скрипты дают каждому «свой» IP)
DASHBOARD_TOKEN=demo OTP_TRUSTED_PROXIES=127.0.0.1 python3 run.py

# 2. браузер (вкладка «Риски» сразу; адрес без #risk открывает «Журнал»)
#    http://localhost:8000/dashboard?token=demo#risk

# 3. сюжет демо в другом терминале
python3 demo_traffic.py --scenario demo --token demo
```

Перед запуском очистите старое состояние, если сервер уже работал: перезапустите `run.py` (всё в памяти).
Без `OTP_TRUSTED_PROXIES` сервер игнорирует `X-Forwarded-For` (так и должно быть), и все события придут
с `127.0.0.1` — скрипты предупредят об этом.

Отдельные атаки:

```bash
python3 attack.py --url http://localhost:8000                     # атаки из ТЗ, как раньше (код выхода 0)
python3 attack.py --only pumping --client-ip 45.13.7.200 --token demo   # только SMS pumping
python3 demo_traffic.py --users 10 --interval 3                   # только фон из обычных пользователей
```

### Через Docker

`docker-compose.yml` уже передаёт `DASHBOARD_TOKEN` и `OTP_TRUSTED_PROXIES` из окружения или `.env`,
править файл не нужно. Но запросы с хоста приходят в контейнер не с `127.0.0.1`, а со шлюза docker-сети,
поэтому доверять нужно ему:

```bash
docker compose up -d --build
docker network inspect "$(basename "$PWD")_default" -f '{{(index .IPAM.Config 0).Gateway}}'   # например 172.18.0.1
DASHBOARD_TOKEN=demo OTP_TRUSTED_PROXIES=172.18.0.1 docker compose up -d   # перезапуск с этими переменными
python3 demo_traffic.py --scenario demo --token demo   # outbox/sms.jsonl смонтирован в корень репозитория
```

Переменные `RISK_*` (в том числе `RISK_LLM_API_KEY`) compose в контейнер **не передаёт** — для них
понадобилась бы правка `docker-compose.yml`, поэтому LLM-сводку показываем только при запуске через `python3 run.py`.

|---|---|---|---|
| 0:00–1:00 | **Этап 1.** Обычные пользователи с разных IP: запрос кода → ввод через 5–20 с; ~15% ошибаются один раз, ~10% бросают | Плитки: уровень «Низкий», конверсия 70–90%. «Подметание» (5 мин) — случайное облако зелёных точек; на графе — точки с одним лучом | «Так выглядит нормальная жизнь: у каждого человека свой IP и свой номер, почти все вводят код.» |
| 1:00–2:30 | **Этап 2.** Бот `45.13.7.200` заказывает SMS на номера подряд раз в ~1,5 с и не вводит коды. Пользователи продолжают входить | Красная линия вдоль низа «Подметания»; «звезда» на графе; тревога «Средний» на 5-м номере и «Высокий» на 6-м; плитка «≈ N сом потрачено ботами» растёт | «Базовая защита пропускает каждую SMS — лимит send только на номер, а номера разные. Модуль рисков поймал бота на шестом номере; в боевом режиме остальные 54 SMS были бы отклонены.» |
| 2:30–2:45 | **Этап 3.** Подбор кода к одному номеру с `77.88.1.15` | В топе IP — «Ошибки ввода +25», «Атака на блок +15», уровень «Средний» | «Сам перебор остановлен ТЗ-защитой — 5 ошибок и блок на 15 минут. Модуль добавляет объяснение: кто и как ломился.» |
| 2:45–3:00 | **Этап 4.** Распределённая атака с `91.200.3.4`: 50 номеров подряд, потом перебор | Балл 100: «Веер», «Подряд», «Без подтверждений», «Ошибки ввода», «Лимит IP»; вторая «звезда» | «Обход блокировки номера через много номеров упирается в лимит 20 проверок в минуту с IP — и сразу видна как высокий риск.» |
| 3:00–3:30 | **Этап 5.** Снова обычные пользователи | Кнопка «Сводка за 10 минут» → три инцидента; клик по боту → карточка и «Почему такой балл» (сумма причин = балл) | «Любое решение объясняется одной строкой. Сводку собирает шаблон; LLM можно включить, но она получает только агрегаты и ничего не решает.» |

Скрипт сам печатает перед каждым этапом заголовок и подсказку «смотрите на дашборде».

## Цифры для слайда

Параметры — из `app/config.py` (ТЗ) и `app/risk/config.py` (модуль рисков).

| Что | Формула | Значение |
|---|---|---|
| Угадать код за одну попытку | 1 / 10⁶ | **0,0001%** |
| Попыток на один номер в сутки | 5 ошибок → блок 900 с ⇒ 86 400 / 900 = 96 циклов × 5 | **480 попыток/сутки** |
| Шанс подобрать код к номеру за сутки | 1 − (1 − 10⁻⁶)⁴⁸⁰ ≈ 480 / 10⁶ | **≈ 0,048%** |
| Потолок попыток с одного IP | 20 verify/мин × 1 440 мин | **28 800 попыток/сутки** (≈ 0,029 угаданных кода в сутки на все номера сразу) |
| На каком номере ловим pumping-бота | 5 номеров подряд без подтверждений: «Подряд» 25 + «Без подтверждений» 25 = 50 (средний); 6-й номер добавляет «Веер» +20 (больше 5 номеров) = 70 ≥ 60 | **на 6-м номере** — уровень «Высокий» |
| Сколько бот «съел» до обнаружения | 6 из 60 SMS при цене `RISK_SMS_PRICE` = 1 сом | **6 сом против 60 сом за всю атаку**; в боевом режиме экономия 54 SMS (90%) |

## Ответы на вопросы жюри

- **Почему модуль не блокирует сам?** Сценарии жюри шлют запросы с одного IP на номера подряд — ровно наши
  признаки бота. Блокировка сломала бы зачётные сценарии и могла бы задеть людей. Поэтому сейчас — режим
  наблюдения: тревога и подпись «в боевом режиме было бы сделано …». Режим enforce — следующий шаг.
- **Университетский Wi-Fi, NAT оператора — много людей за одним IP?** «Веер» сам по себе даёт 20 баллов —
  это уровень «Низкий». Высокий уровень требует сочетания: номера **подряд**, коды **не вводятся**, ошибки.
  У живых людей за NAT номера случайные и конверсия 70–90%.
- **Почему ночь даёт мало баллов?** Ночью тоже входят живые люди (смены, другой часовой пояс). Ночь (+10)
  только усиливает другие признаки и в одиночку уровень не поднимает.
- **Откуда пороги и как их менять?** Значения подобраны по поведению людей и бота на симуляции и описаны в
  `app/risk/config.py`. Любой порог меняется без кода: `RISK_<ПОЛЕ>`, например `RISK_WINDOW=300`,
  `RISK_HIGH_AT=70`, `RISK_SMS_PRICE=2.5`.
- **Почему номера не хранятся?** Полный номер приходит в модуль один раз и сразу превращается в псевдоним
  `HMAC-SHA256(ключ, номер)`, последние 4 цифры и маску `+996700***456`. В API, логах и сводке полных номеров
  нет — это проверяют тесты (`996\d{9}` не встречается ни в одном ответе).
- **Что будет при сбое модуля?** События идут через асинхронную очередь: запрос пользователя только кладёт
  событие и не ждёт. Переполнение очереди — событие отбрасывается (`dropped` в подвале вкладки). Исключения
  модуля перехватываются (`errors`). Ответы `/otp/*` с модулем и без него совпадают байт в байт — есть тест.
  `RISK_ENABLED=0` выключает модуль целиком.
- **Зачем LLM и почему она не принимает решений?** Только чтобы пересказать сводку человеческим языком для
  дежурного. Включается ключом `RISK_LLM_API_KEY`, получает лишь JSON с агрегатами (без номеров, кодов и
  событий), при ошибке или таймауте 5 с — шаблон. Баллы, уровни и тревоги считает детерминированный код.
- **Что дальше?** Режим enforce (отказ 429 для уровня «Высокий»); лимит send по IP и подсети в самом
  сервисе; хранение состояния модуля в Redis для нескольких экземпляров; проверка конверсии по диапазонам
  номеров.
